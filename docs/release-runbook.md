# Desktop release runbook

## Manual workflow dispatch

The `Release desktop installers` workflow accepts a `mode` on `workflow_dispatch`. `target` defaults to `macos` and is always honored: `macos` does not start Windows jobs, and `windows` does not start macOS jobs.

- `development` (default): unsigned Dev packages, no signing or public publication. Packages are stored in a per-run draft GitHub Release (`dev-<run_id>-<run_attempt>`); its location is recorded in the validation job summary.
- `signed`: production-identity signed packages. Fill `signed_version` with a non-`v` semver such as `0.9.2-test.1`. Every target uses a draft GitHub Release for handoff, then publishes to ModelScope `releases/test/<version>/`. `target=all` also updates `releases/test/latest/`. The GitHub Release stays a draft and is not marked pre-release. After public metadata and installer downloads are verified, Feishu receives the selected platforms' ModelScope download links. These builds check the public stable update feed; draft and ModelScope test-channel builds are not offered as online updates.
- `prerelease`: production-identity signed packages. Fill `prerelease_tag` with a non-`v` semver such as `2.1.0-rc.1`. When `target=all`, publish to GitHub `--prerelease` and ModelScope `releases/prerelease/<tag>/` plus `releases/prerelease/latest/`. A single-platform prerelease signs that platform and skips publish.

Official releases are still created by pushing a `v*` tag, not by filling the dispatch form. Do not put `v0.9.1` in `prerelease_tag` or `signed_version`.

Installed production-identity macOS and Windows builds check the public stable feed on startup, every six hours, after a sufficiently long sleep, and on manual request. Unpackaged and isolated Dev builds do not check this feed. Downloads begin only after user consent; installation requires an explicit restart action. Prereleases and downgrades are not offered. The package metadata points to `https://dshdesktop.com/work/updates/latest/`. On the existing `dshdesktop.com` HTTPS server, include [`ops/nginx/work-updates.conf`](../ops/nginx/work-updates.conf); it redirects each update asset to `alexyaojin/bisheng-work/releases/latest/` on ModelScope. The `/work/` prefix keeps this feed separate from DSH Desktop's `/updates/latest/`. No GitHub token is needed in the app. Older builds with the hard-disabled updater require one manual installation of a build containing the enabled updater before they can receive online updates. Feed metadata availability alone does not establish installed-app download and restart acceptance on either platform.

Before publishing a formal release, verify that a request to `https://dshdesktop.com/work/updates/latest/latest.yml` receives a 302 with the BISHENG ModelScope URL, then verify that metadata and each referenced ZIP, installer, and blockmap can be downloaded through this route. The first public metadata will be absent until a formal release is mirrored. Browser pages under `dshdesktop.com/work/` share an origin with the DSH Desktop site, but a redirect to ModelScope still changes origin for browser fetches; serve those responses from the site or configure CORS if a future web page needs to read them in JavaScript.

## Build layout and timing

Before starting the hosted Windows job, `windows-preflight` runs type checking and portable release, handoff, PE-signing selection, and update-metadata tests on the ARM64 self-hosted worker. These checks also run for Windows-only dispatches. The default Windows subset omits those portable tests; the optional complete Windows suite still includes them. Native dependency installation, Office/PPT preparation, application packaging, recovery UI checks, and packaged Windows runtime verification remain on Windows.

Signed, prerelease, and formal builds use `package:win:unpacked`: Windows builds the application directory and uploads only `win-unpacked.tar.gz`. After the packaged Harness smoke, the workflow terminates the complete copied-app process tree and removes that large temporary copy before archiving. The handoff archive is then created by `scripts/archive-windows-unpacked.mjs` with the repository's pinned Node `tar` implementation; it does not depend on the hosted image's `tar.exe`, and it rejects a missing source or empty archive explicitly. The self-hosted UKey stage verifies that archive, signs its PE files, builds the NSIS installer once with `--prepackaged`, and generates final update metadata. Windows no longer builds or uploads an unsigned installer that the signer would replace. Development builds retain `package:dev:win` to produce a directly usable unsigned installer.

CI builds each native application once, preparing Office/PPT inputs in that build, then invokes `npx --no-install vitest run` directly so npm pretest hooks do not assemble the inputs again. Windows uses `--config vitest.windows.config.ts` by default: serial platform regressions for Windows UI/process behavior, paths (including workbench junction containment and Office engine resolution), Profile and generation loading, packaging, and updates. The ARM64 macOS job runs the full suite; Intel retains native build and packaged-runtime checks without a second full suite. Enable `windows_full_tests` on manual dispatch when changing shared runtime dependencies or investigating a Windows-specific regression that falls outside this subset. New Windows regressions must be included in `vitest.windows.config.ts` if their filename does not match an existing pattern.

After the single application build and tests, CI calls the Windows builder adapter directly to package the existing output. This retains the custom directory installer and signing hooks without calling a `package:*` script that would build again. The three-scale recovery UI check is opt-in with `windows_recovery_ui`; enable it when changing recovery pages, Safe Mode, titlebars, or display scaling. It captures screenshots and verifies recovery actions and layout at 100%, 125%, and 150% on native Windows. Diagnostics are archived as `windows-recovery-ui.tar.gz` in the development draft Release when requested, including after a failed UI check if files were produced.

The packaged Harness smoke remains enabled for manual Windows dispatches. It runs the unpacked application outside the repository, checks the bundled Node and Koffi native binding, reaches authenticated Harness HTTP/RPC, creates a workspace and session, and checks for crashes or runtime errors. It does not establish visual UI activation or final signed-installer installation/upgrade acceptance. Formal tag runs retain their existing behavior and do not run this smoke.

Local `npm test` and `package:*` commands still prepare their own inputs. Local `npm run test:windows` prepares only PPT, without the Python/Office payload. Installers are uploaded directly as GitHub Release assets without an additional archive. Formal publication reuses the full history fetched by checkout and installs Copilot once for both GitHub and Feishu notes; both note validators and deterministic fallbacks remain enabled. The obsolete DSH archive-backfill workflow and orphaned version-index declaration have been removed: BISHENG does not expose that rollback index, and the old workflow targeted the DSH repository. Existing remote archives are unaffected.

No workflow uses Actions artifact upload/download. Development packages and recovery diagnostics use a per-run draft Release; all signed, prerelease (including single-platform), and formal builds use their versioned draft Release for cross-job handoff. Draft assets do not expire automatically: delete obsolete drafts manually after downloads and diagnosis are complete. The old Actions artifact retention policy does not affect these drafts, and historical Actions artifacts remain until deleted or expired.

The macOS jobs stage signed assets, the Windows build stages unsigned inputs, and the UKey job replaces them with signed Windows assets. Every Windows signing handoff checks downloaded sizes and SHA-256 digests. Publish jobs verify the complete release set when all platforms are present and upload it to the corresponding ModelScope path. Formal and complete pre-release runs then check public metadata and prune the draft Release to the two DMGs and Windows EXE before publication. Signed and single-platform prerelease runs leave their GitHub Release as a draft. ModelScope retains the ZIPs, blockmaps, and update metadata needed by the updater. GitHub generates source-code archives from the tag separately. A failed run leaves the draft for inspection and retry; it must not be presented as a published release.

The self-hosted signer downloads every handoff, including single-platform prereleases, from the draft GitHub Release and verifies staging checksums before extraction.

PPT packages are generated under `.build/ppt-runtime/packages/` and overlaid into the Electron package. The `afterPack` gate checks ASAR unpacking, the generated `dsh-ppt` and `dsh-ppt-composer` payloads, and the offline Office runtime. A successful source build alone does not verify the packaged paths.

## Rebuilding a macOS installer from an existing app

Pass the `.app` bundle itself to `--prepackaged`, for example `--prepackaged "dist-dev/mac-arm64/BISHENG Dev.app"`. Electron Builder treats this argument as the application bundle and copies it into the image under the product name. Passing the containing `mac-arm64` directory creates a nested `.app` directory that Finder cannot launch.

Before delivering a rebuilt DMG, mount it read-only and check the top-level application has `Contents/Info.plist`, its executable in `Contents/MacOS/`, and `Contents/Resources/app.asar`. Compare the mounted ASAR and enterprise plugin files against the selected build. Store artifacts in a distinct delivery folder with their commit and SHA-256 checksums.

## macOS packaging runners

Both macOS jobs use self-hosted workers on the ARM64 Mac. Apple Silicon uses the organization runner with `self-hosted`, `macOS`, and `ARM64` labels and ARM64 Node 22. Intel uses a dedicated repository runner with `self-hosted`, `macOS`, and `bisheng-intel` labels. It requires Rosetta 2, uses x64 Node 22, and runs shell commands under `arch -x86_64 /bin/bash`. The job sets `npm_config_arch=x64` so Electron's installer does not replace the x64 binary with arm64 after detecting Rosetta; npm still installs the x64 `node-addon-require-builtin` binding from `process.arch`. `verify-target` checks the executing platform and architecture and probes the Harness native loader under Electron Node mode.

Each runner instance has its own installation directory, `_work` workspace, and temporary directory. Build preparation and tests can run concurrently across the two jobs. In CI, the ARM64 full suite runs test files serially to leave CPU and disk headroom for Intel packaging; Intel does not repeat that suite. When running the Office integration suite locally under Intel Node, separate bounded timeouts cover Python/Electron cold starts, Harness readiness, and the two-start Safe Mode recovery scenario. When runners use the same macOS user, the two macOS jobs acquire `~/.cache/bisheng-macos-signing.lock` before preparing a signing keychain and release it after cleanup, serializing only the signing/package phase that modifies the shared keychain search list. A wait exceeding 30 minutes fails with a diagnostic; after a runner crash, confirm its signing job has stopped before removing a stale lock. Other repositories sharing this user must coordinate their signing separately; this lock applies to this repository's jobs.

Install Rosetta once if needed (`softwareupdate --install-rosetta --agree-to-license`). Configure the dedicated Intel worker independently with `config.sh --no-default-labels --labels self-hosted,macOS,bisheng-intel`, then install/start its own `svc.sh` LaunchAgent. Omitting `ARM64` from this worker's routing labels keeps the Apple Silicon build and UKey signer on the original organization worker. Do not copy an existing runner's `.runner` or credentials. With 16 GB RAM, start with two Bisheng workers rather than adding more build instances; the existing DSH worker also shares machine resources.

Shared runtime asset preparation uses the existing ARM64 self-hosted macOS worker, with local npm downloads and a five-minute Node setup timeout. Dispatch validation and publication jobs use GitHub-hosted Ubuntu workers; the Windows build job uses a GitHub-hosted Windows worker. Windows preflight and UKey signing use the self-hosted macOS worker, alongside the two macOS packaging workers. Publication requires Node 22, Python 3 with venv support, and GitHub CLI. An offline self-hosted worker blocks the jobs assigned to it; there is no fallback runner.

The persistent macOS workers use their local npm download cache. Their `setup-node` steps do not restore or upload the Actions npm cache: a 1.35 GB restore took about 10 minutes and ended with a server authentication warning during a signed run; the Node setup step took over 20 minutes overall. Node setup is bounded to five minutes. Native build and persistent-worker `npm ci` steps use `--prefer-offline`, reusing cached downloads while still installing from the lockfile and running existing lifecycle scripts unless explicitly disabled for release tooling. Clearing the local npm cache is safe, but the next `npm ci` must download packages again.

The GitHub-hosted Windows job uses `setup-node`'s npm cache keyed by `package-lock.json`, plus a separate cache for Electron, electron-builder, and SHA-verified Office runtime downloads. The packaging cache is scoped to Windows x64 and the dependency/Office lockfiles, with a Windows x64 fallback for reusable downloads after dependency changes. A cache miss downloads dependencies normally; neither cache stores `node_modules` or replaces the native build and verification steps.

Before dispatching, confirm that GitHub Actions is enabled for this repository, that the organization runner group grants it access, and that the runner is online. Do not install dependencies on the runner's persistent checkout by hand; each job uses `npm ci`.

For a first packaging check, dispatch `Release desktop installers` on `main` with `target=macos` and `mode=development`. This creates unsigned, isolated Dev packages in the per-run draft Release and does not publish them publicly. Signed builds additionally require the Apple signing and notarization secrets listed in the workflow. Verify both architecture artifacts and their bundled runtime before using a signed package as a release candidate.

## GitHub Actions parameters for signing and publishing

Add these under **Settings → Secrets and variables → Actions** for this repository. Existing secrets in CoAligne or DSH Desktop cannot be read back through GitHub and are not automatically available to BISHENG. The same Apple certificate and API key may be reused only if their owner confirms that this app should be signed under that Apple team.

| Secret | Needed for | Value to provide |
| --- | --- | --- |
| `DESKTOP_CSC_LINK` | Signed macOS | Base64 PKCS#12 Developer ID Application certificate, or a supported HTTPS source |
| `DESKTOP_CSC_KEY_PASSWORD` | Signed macOS | Password for that PKCS#12 certificate |
| `DESKTOP_APPLE_API_KEY` | Signed macOS | Raw App Store Connect `.p8` key contents for notarization |
| `DESKTOP_APPLE_API_KEY_ID` | Signed macOS | Key ID for the `.p8` key |
| `DESKTOP_APPLE_API_ISSUER` | Signed macOS | App Store Connect issuer UUID |
| `DESKTOP_APPLE_TEAM_ID` | Signed macOS | Apple Developer team ID matching the certificate and notarization key |
| `DESKTOP_WINDOWS_SIGNING_PIN` | Signed Windows | PIN for the SafeNet UKey connected to the local runner |

`MODELS_TOKEN` only enables generated release notes; the workflow has a deterministic fallback. `FEISHU_RELEASE_WEBHOOK` is required for `signed` test builds and enables optional notifications for formal and pre-release runs. Signed dispatches check it before packaging; download verification or notification failure fails the publish job. GitHub supplies `GITHUB_TOKEN` automatically for GitHub Release publication. Formal `v*`, complete `prerelease`, and `signed` runs require the repository secret `MODELSCOPE_TOKEN` with write access to `alexyaojin/bisheng-work`; the workflow checks it before packaging. Formal assets go to `releases/archive/<version>/` and `releases/latest/`. Pre-release assets go to `releases/prerelease/<tag>/` and `releases/prerelease/latest/`. Signed test assets go to `releases/test/<version>/`, and a complete signed run also updates `releases/test/latest/`. None of these paths changes the formal update feed. `CRASH_ADMIN_TOKEN` and CoAligne's GCP parameters are not used by this workflow.

For a signed test build, dispatch `mode=signed` with a non-`v` `signed_version`. `target=all` publishes both ModelScope test paths. `target=macos` or `target=windows` publishes only that platform under `releases/test/<version>/`. The GitHub Release remains a draft in every signed run. Complete pre-releases and formal tag releases require both macOS architectures and Windows signing before ModelScope and GitHub publication can finish.

The build rejects external main/preload imports absent from the packaged dependency contract. Before signing, afterPack verifies unpacked resource sizes/hashes, production dependency manifests and required Harness peers, then runs a temporary Safe Mode Harness, authenticated HTML/bootstrap registration, node-pty and speech native loading with the packaged Electron runtime. The signed Windows smoke repeats the runtime probe using installed paths and does not require checkout dependencies. This probe does not establish browser UI activation or a successful model request; perform native UI acceptance separately. The unpacked hashes belong to the pre-sign payload and must not be compared against binaries changed by signing. `node scripts/verify-desktop-navigation.mjs` is an additional interactive-desktop check of splash rendering and window navigation cancellation.

## macOS app notarization retries

App notarization runs in `scripts/notarize-macos.mjs`, an `afterSign` hook that finishes before DMG/ZIP creation. The built-in electron-builder notarization is disabled to avoid duplicate submissions. Both macOS jobs run on Apple Silicon. The already-working arm64 build uses `/usr/bin/xcrun` directly; only the Intel matrix entry places a narrow `xcrun` bridge at the front of `PATH` that executes `/usr/bin/xcrun` as arm64. This keeps `@electron/notarize` on the installed Xcode toolchain when the Intel package is built by an x64 Node process under Rosetta. Each route checks `xcrun --find notarytool` before signing starts. The hook uses the existing `@electron/notarize` API for submission and acceptance, then recovers only stapling failures 65/68/69 with up to five fresh `xcrun stapler staple` calls, waiting 10/20/30/40/50 seconds and limiting each call to 60 seconds. Retry subprocess timeouts are also retried. Rejected notarization and permanent errors fail immediately; successful stapling must pass `stapler validate`. The later DMG stapling and validation retain their existing workflow retries. A network error talking to Apple CloudKit during app stapling therefore no longer requires a fresh notarization submission.

## Local Windows UKey signing runner

Windows packaging and signing run as separate jobs. For signed builds, the GitHub-hosted Windows runner builds an unsigned application directory and archives it; development builds still produce an unsigned NSIS installer. Formal tag, signed, and all pre-release runs stage unsigned inputs in a draft GitHub Release. A local macOS ARM64 runner downloads the inputs, verifies draft-asset digests for every handoff, scans every PE by content, preserves existing vendor signatures, and signs unsigned PEs with Jsign and the SafeNet UKey. It signs the NSIS extraction helper and generated uninstaller during repackaging, then signs the final installer, regenerates the blockmap and `latest.yml`, and stages the signed release set. Any missing archive, invalid digest, signing failure or repackaging failure stops the run. A separate Windows installed-artifact smoke remains required before claiming installation acceptance; signing and release-set verification alone do not establish it.

The pinned Windows NSIS template stages the application in a sibling directory before closing the old app, then renames the old directory to a backup and promotes the staged directory. A failed extraction or rename restores the previous installation. The available signed-installer smoke script also locks the old executable to verify that a failed upgrade leaves it runnable, but the current release workflow does not invoke that script. A user-selected different directory is an independent installation: the installer does not automatically uninstall the previous directory, which remains available until the user removes it. Keep the user-selected installation directory when changing this template; the build adapter rejects unexpected upstream template changes.

Runtime dependencies are unpacked beside `app.asar` because Harness, pnpm, native addons, and the standalone Windows Node process need physical paths. The macOS ARM64 test package contains a 6.2 MB `app.asar` and about 588 MB of unpacked dependencies; enabling asar alone did not reduce its 256 MB DMG. Do not remove `node.exe` from Windows yet: the pinned `node-addon-require-builtin@0.1.6` rejects Electron 43.4.0 in RunAsNode mode during Harness boot, even though the Koffi native probe passes ([Windows CI evidence](https://github.com/dataelement/dsh-desktop/actions/runs/35972303467)). Repeat the packaged Windows Harness and final signed-installer gates after a loader version explicitly supports the target Electron fingerprint before revisiting that removal.

Prepare the local runner once:

1. Register it with the `self-hosted`, `macOS`, and `ARM64` labels.
2. Install SafeNet Authentication Client and confirm `/usr/local/lib/libeTPkcs11.dylib` is readable.
3. Connect the UKey before pushing a release tag.
4. In the GitHub repository, open **Settings → Secrets and variables → Actions** and create a repository secret named `DESKTOP_WINDOWS_SIGNING_PIN` containing the UKey PIN. For stronger release controls, use an environment secret and add the matching `environment` to the `sign-windows` job.
5. Restrict release tag creation and workflow changes to trusted maintainers. A self-hosted runner can access any secret injected into its job.

The persistent UKey signing worker uses its local npm download cache. Its `setup-node` step does not restore or upload the Actions npm cache, and Node setup is bounded to five minutes. GitHub-hosted build and publish jobs continue using the Actions cache. Clearing the local npm cache is safe, but the next `npm ci` must download packages again.

The workflow pins Jsign 7.5 by SHA-256 and uses the SafeNet `ETOKEN` store, SHA-256 signing, and a DigiCert RFC 3161 timestamp. GitHub injects the PIN only into the signing step. The step copies it to a mode-`600` temporary file, removes it from the shell environment, and deletes the file when the step exits. The workflow never prints the PIN or passes it as a command-line argument.

The configured update publisher is `Beijing Shuju Xiangsu Intelligence Technology Co., Ltd.`, taken from the signed v0.9.2 installer. If the signing certificate changes, update `build.win.signtoolOptions.publisherName` only after checking the new certificate subject and the updater's signature verification on an installed Windows build. After a tag release succeeds, verify that the Windows installer shows the expected publisher and a valid RFC 3161 timestamp in its Digital Signatures properties. Never reuse a published tag; fix the issue and release a new version.
